## 1. 개요 및 법적·제도적 점검 근거

### 1.1 점검 목적

- iCReaT에 저장된 연구과제 정보, 연구대상자 개인정보 및 임상·건강정보(민감정보)에 대한 보호 통제가 관련 법령과 국가 지침을 충족하는지 사전 점검함
- G-Cloud 환경에서 외주 개발·운영 구조로 인해 발생할 수 있는 비인가 접근 경로를 식별함
- 국정원 보안성 검토 시 지적 가능 사항을 사전에 파악하여 보완함
- 외주 운영사로부터 서면 증빙을 확보하여 통제 이행 수준을 객관적으로 입증함

### 1.2 점검 대상 시스템 현황

| 구분 | 내용 |
| --- | --- |
| 취급 정보 | 연구과제 정보, 연구대상자 개인정보, 임상·건강정보(민감정보) |
| 사용자 | 임상연구 과제 수행 연구자(PI, CRC, CRA, Data Manager) |
| 권한 체계 | 일반 과제 담당자(소속 과제만 조회·다운로드), 최고 관리자(전체 과제 통합 조회·일괄 다운로드) |
| 인증 방식 | 계정·비밀번호 인증, 3개월 주기 비밀번호 변경, 전자서명(e-Sign) 별도 운영 |
| 운영 구조 | 외주 업체 개발·운영, 데이터 백업 시스템 및 관리자 전용 서버 접근 경로 운영 |

### 1.3 점검 범위 및 한계

| 구분 | 내용 |
| --- | --- |
| 수행 범위 | ① 문서·설정 검토 ② 외주사 서면 소명 및 증빙 검토 ③ 서비스 로그인 페이지 외부 관찰(일반 사용자 열람 수준) |
| 제외 범위 | 운영 시스템 직접 침투 시험, 로그인 시도, 파라미터 조작, 비공개 경로 탐색, 반복·자동화 요청 |
| 한계 | 권한 검증, 세션 관리, 다운로드 로직, 감사로그 등 로그인 이후 서버 동작은 외부 관찰로 판단할 수 없으며, 외주사 증빙 및 승인된 모의해킹으로 확인함 |
| 위협 기술의 성격 | 2·3장의 위협 내용은 취약점 존재를 확인한 것이 아니라 점검·증빙 확인이 필요한 가능성을 기술한 것임 |

### 1.4 위험도 분류 기준

| 위험도 | 정의 | 조치 시점 |
| --- | --- | --- |
| Critical | 대량 개인정보 유출 또는 시스템 통제권 상실로 직결될 수 있음 | 즉시~단기 |
| High | 단독 또는 다른 취약점과 결합 시 중대한 유출·침해로 이어질 수 있음 | 단기 |
| Medium | 단독으로는 피해가 제한적이나 다른 공격의 성공 가능성을 높임 | 단기~중기 |

### 1.5 서비스 주소 외부 관찰 결과 (2026. 11. 5.)

로그인 페이지를 비로그인 상태로 1회 열람하여 수신된 응답과 페이지 구성을 관찰함.

| 번호 | 관찰 내용 | 판정 | 관련 근거 |
| --- | --- | --- | --- |
| O-1 | HTTPS로 서비스되며, 비암호화(HTTP) 혼합 리소스 없음 | 양호 | [R3] 제7조, [R7] V9 |
| O-2 | Server 헤더에 웹서버 제품·버전 미노출 | 양호 | [R7] V14 |
| O-3 | 스크립트 접근 가능 쿠키는 성능 모니터링용 1종이며, 세션 쿠키는 스크립트에 미노출 | 양호(증빙 확인 필요) | [R7] V3 |
| O-4 | 지원 종료 프론트엔드 라이브러리 사용: AngularJS 1.2.9(2021. 12. 지원 종료), jQuery 1.11.2, jQuery UI 1.11.2 | 개선 필요(High) | [R5] 제50조, [R6] API8, [R7] V14 |
| O-5 | 브라우저 보안 헤더(Strict-Transport-Security, Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy) 응답에서 미확인 | 개선 필요(Medium) | [R6] API8, [R7] V14 |

> ※ O-4는 사용 버전 기준의 잠재 위험(공개 XSS 취약점 다수)이며, 실제 영향은 해당 기능 사용 여부에 따라 달라지므로 외주사 영향 분석을 요구함.
> ※ O-5는 G-Cloud 앞단 장비(웹방화벽·부하분산기)에서 일부 경로에만 적용될 수 있으므로 설정 증빙으로 최종 확인함.

## 2. [섹션 A] 국정원 G-Cloud 보안성 검토 필수 점검 항목 (정부 규정 기반)

### A-1. 계정 및 권한 관리 통제 미흡

**① 위협명 및 위험도**

- 계정 공유, 과다 권한 부여, 퇴직·전보자 권한 미말소로 인한 비인가 접근
- 위험도: **Critical**

**② 관련 법령·규정 출처**

- [R3] 제5조(접근 권한의 관리): 업무 수행에 필요한 최소 범위로 차등 부여, 업무 변경 시 지체 없이 변경·말소, 부여·변경·말소 내역 최소 3년 보관, 취급자별 계정 발급 및 공유 금지
- [R1] 계정관리 분야
- [R4] 계정·권한 관리 통제 항목
- [R7] V4(접근 통제)

**③ 시스템 영향도**

- 최고 관리자 권한이 과다 부여되거나 공유되면 단일 계정 침해로 전체 과제 임상데이터가 노출됨
- 외주 인력 철수 후 계정이 남아 있으면 외부인의 정상 계정 접근 경로가 됨
- 공유 계정 사용 시 행위자 특정이 불가하여 사고 원인 규명과 책임 확인이 어려움
- [R3] 제5조 미이행은 보안성 검토 지적 및 개인정보 침해 사고 시 기관 책임 사유가 됨

**④ 기술적·관리적 보완 요구사항**

- [관리] 사용자·관리자·외주 인력 계정 대장 정비, 공유 계정 전면 폐지
- [관리] 권한 부여·변경·말소 이력 3년 이상 보관 및 분기별 정기 검토
- [관리] 최고 관리자 계정 수 최소화 및 지정 사유 문서화
- [기술] 장기 미사용 계정 자동 잠금, 퇴직·전보·외주 철수 시 즉시 말소 절차 시스템화

### A-2. G-Cloud 망분리 및 외주사 원격접근 통제

**① 위협명 및 위험도**

- G-Cloud 접근 정책을 벗어난 원격 유지보수 경로, 하드코딩 계정, 디버그 기능 잔존을 통한 인증 우회 접근
- 위험도: **Critical**

**② 관련 법령·규정 출처**

- [R1] 접근통제 분야(관리자 접근 경로, 외부 접속 통제)
- [R3] 제6조(접근통제): IP 주소 등에 의한 접속 권한 제한, 외부 접속 시 인증서·보안토큰·일회용 비밀번호 등 안전한 인증수단 적용, 일정 시간 미사용 시 자동 접속 차단
- [R4] 접근통제 통제 항목
- [R6] API8(보안 설정 오류), API9(부적절한 자산 관리)

**③ 시스템 영향도**

- 승인되지 않은 원격 접속 경로나 하드코딩 계정은 인증·권한 통제 전체를 우회하며, 정상 접근과 구분되지 않아 탐지가 어려움
- 운영 환경에 남은 테스트 계정·디버그 엔드포인트·API 문서 페이지는 내부 구조 노출과 비인가 기능 호출로 이어짐
- 「개인정보 보호법」상 처리 위탁자로서 수탁자(외주사) 관리·감독 의무가 있으므로, 외주사 경로로 인한 사고도 기관 책임으로 귀결됨

**④ 기술적·관리적 보완 요구사항**

- [기술] 원격 유지보수는 승인된 단일 경로(전용 접속망·VPN·접근통제 시스템)로 한정하고 접속 IP 제한 적용
- [기술] 원격 접속에 개인별 계정과 안전한 인증수단(다중인증) 적용, 접속·명령 기록 보관
- [기술] 소스코드·설정파일 내 하드코딩 계정·비밀번호·API 키 제거 및 별도 비밀정보 관리 체계 적용
- [기술] 운영 환경의 테스트 계정, 디버그 기능, API 문서 페이지 제거 또는 접근 차단
- [관리] 외주사 원격 접속 사전 승인·사후 검토 절차 수립, 보안서약서 징구

### A-3. 임상 데이터 및 백업 저장소 암호화 미흡

**① 위협명 및 위험도**

- 데이터베이스·첨부파일·백업 데이터의 평문 저장 및 전송 구간 암호화 미흡
- 위험도: **Critical**

**② 관련 법령·규정 출처**

- [R2] 제29조(안전조치의무)
- [R3] 제7조(개인정보의 암호화): 인증정보의 저장·송수신 시 암호화, 비밀번호 일방향 암호화 저장, 고유식별정보 등 저장 시 암호화, 인터넷망 송수신 시 암호화, 암호 키 관리 절차 수립
- [R1] 암호화 분야
- [R4] 암호화 통제 항목
- [R7] V6(저장 데이터 암호화), V9(통신)

**③ 시스템 영향도**

- 백업 저장소는 전체 데이터를 담고 있으나 운영 서버보다 통제가 느슨한 경우가 많아, 백업 접근만으로 전체 데이터가 유출될 수 있음
- 암호 키가 데이터와 같은 위치에 보관되면 암호화의 실효성이 없어짐
- 평문 저장 상태에서 유출되면 [R3] 제7조 위반과 함께 대규모 민감정보 유출 사고로 확대됨

**④ 기술적·관리적 보완 요구사항**

- [기술] 고유식별정보·인증정보 암호화 저장, 비밀번호 일방향 암호화(안전한 해시 알고리즘) 확인
- [기술] 임상·건강정보(민감정보)에 대한 저장 암호화 적용 범위 확정 및 적용
- [기술] 백업 데이터 암호화, 백업 접근 권한자 최소화, 백업 접근 기록 보관
- [기술] 암호 키를 데이터와 분리 보관하고 키 생성·이용·보관·배포·파기 절차 수립
- [기술] 전 구간 TLS 적용 및 HTTPS 강제 헤더(HSTS) 적용(1.5절 O-5)

---

### A-4. 비밀번호 정책 및 다중인증(MFA) 부재

**① 위협명 및 위험도**

- 반복 대입 공격 차단 미흡, 주기적 변경 정책의 회피, 관리자·외부 접속 다중인증 부재
- 위험도: **High** (최고 관리자 계정 대상 시 Critical)

**② 관련 법령·규정 출처**

- [R1] 인증 분야
- [R3] 제5조(접근 권한의 관리): 일정 횟수 이상 인증 실패 시 개인정보처리시스템 접근 제한
- [R3] 제6조(접근통제): 외부 접속 시 안전한 인증수단 적용, 일정 시간 미사용 시 자동 접속 차단
- [R4] 사용자 인증 통제 항목
- [R6] API2(인증 취약), [R7] V2(인증), V3(세션 관리)

**③ 시스템 영향도**

- 3개월 주기 변경만으로는 계정 탈취를 막지 못하며, 숫자만 바꾸는 등 예측 가능한 비밀번호가 늘어날 수 있음
- 실패 횟수 제한이 없으면 자동화된 대입 공격과 타 서비스 유출 계정 대입에 취약함
- 최고 관리자 계정이 비밀번호 단일 요소로만 보호되면 단일 실패 지점이 됨
- 세션 재발급·만료·폐기가 미흡하면 탈취된 세션이 장기간 재사용됨

**④ 기술적·관리적 보완 요구사항**

- [기술] 로그인 실패 허용 횟수 제한 및 계정 잠금, 자동화 방지 장치 적용
- [기술] 최고 관리자 및 외부 접속 계정에 다중인증 의무 적용
- [기술] 로그인 시 세션 재발급, 유휴 시간 자동 종료, 로그아웃 시 서버측 세션 폐기, 쿠키 보호 속성(Secure·HttpOnly·SameSite) 적용
- [관리] 비밀번호 길이·복잡도·재사용 금지 기준을 [R1]·[R4] 기준에 맞게 강화하고, 주기적 변경 정책의 실효성 재검토

---

### A-5. 접속기록(로그) 생성·무결성 보장 및 이상징후 탐지 미흡

**① 위협명 및 위험도**

- 대량 다운로드·관리자 행위 기록 누락, 로그 위·변조 방지 부재, 실시간 경보 체계 미흡
- 위험도: **High**

**② 관련 법령·규정 출처**

- [R3] 제8조(접속기록의 보관 및 점검): 접속기록 1년 이상 보관(민감정보 처리 시스템은 2년 이상), 월 1회 이상 점검, 개인정보 다운로드 확인 시 사유 확인, 위·변조·도난·분실 방지 조치
- [R3] 제6조(접근통제): 개인정보 유출 시도 탐지 및 대응
- [R1] 접속기록 분야, [R4] 로깅 및 모니터링 통제 항목
- [R7] V7(오류 처리 및 로깅)

**③ 시스템 영향도**

- 조회·다운로드·권한 변경 행위가 누락되면 사고 발생 시 유출 범위와 시점을 특정할 수 없어 정보주체 통지와 신고를 정확히 수행하기 어려움
- 로그가 운영 서버에만 저장되고 관리자 권한으로 삭제 가능하면 침해 흔적이 제거될 수 있음
- 경보 규칙이 없으면 로그가 있어도 침해를 실시간으로 인지하지 못함
- [R3] 제8조의 보관·점검·사유 확인 의무 미이행은 그 자체로 법적 미준수에 해당함

**④ 기술적·관리적 보완 요구사항**

- [기술] 접속기록 항목 표준화: 계정, 접속일시, 접속지, 처리한 정보주체 정보, 수행 업무
- [기술] 로그를 운영 서버와 분리된 저장소에 보관하고 위·변조 방지(WORM 등) 적용, 2년 이상 보관
- [기술] 이상징후 경보 규칙 수립(야간 관리자 접속, 비승인 IP, 대량 다운로드, 권한 변경) 및 기관 담당자 동시 수신
- [관리] 월 1회 이상 접속기록 점검, 다운로드 사유 확인 절차 운영, 점검 결과 기록
- [관리] 로그 검토 주체를 운영 주체(외주사)와 분리하여 기관 담당자가 직접 열람·점검

## 3. [섹션 B] 웹 애플리케이션 추가 기술 점검 항목 (OWASP/ASVS 기준)

### B-1. 객체 수준 권한 검증 미흡 (BOLA)

**① 위협명 및 위험도**

- 과제·파일 식별자 조작을 통한 타 과제 데이터 수평적 무단 접근
- 위험도: **Critical**

**② 관련 근거**

- [R6] API1(객체 수준 권한 검증 실패), [R7] V4(접근 통제)
- [R3] 제5조(최소 범위 차등 권한 부여의 기술적 구현)
- [R5] 제50조(SW 보안약점 진단: 부적절한 인가)

**③ 현상 및 시스템 영향도**

- 로그인은 "누구인가"(인증)만 확인하며, "이 자료에 접근할 자격이 있는가"(권한 확인)는 요청마다 서버에서 별도로 확인해야 함
- 서버가 요청의 과제 ID·파일 ID가 요청자 소속 과제의 것인지 검증하지 않으면, 정상 로그인한 사용자가 식별자 값만 바꾸어 타 과제 자료에 접근함
- 과제 간 데이터 분리 원칙이 무력화되어 단일 계정으로 전체 과제의 임상·개인정보 열람·반출이 가능해짐

**④ 기술적 보완 요구사항**

- 모든 조회·수정·다운로드 요청에 서버측 객체 소속 검증 적용
- 외부 노출 식별자를 추정 불가능한 값(UUID 등)으로 전환
- 권한 판단은 클라이언트 전송값이 아닌 서버 세션 정보만을 기준으로 수행

---

### B-2. 기능 수준 권한 검증 미흡 (BFLA) 및 속성 변조 (Mass Assignment)

**① 위협명 및 위험도**

- 일반 계정의 관리자 기능 직접 호출 및 권한 필드 조작을 통한 수직적 권한 상승
- 위험도: **Critical**

**② 관련 근거**

- [R6] API5(기능 수준 권한 검증 실패), API3(객체 속성 수준 권한 검증 실패), [R7] V4(접근 통제)
- [R3] 제5조, [R5] 제50조

**③ 현상 및 시스템 영향도**

- 관리자 메뉴를 화면에서 숨기는 것은 표시 방식일 뿐 접근 통제가 아님. 서버가 요청마다 역할을 확인하지 않으면 정상 로그인한 일반 계정이 관리자 기능 주소로 직접 요청할 때 차단되지 않음
- 정보 수정 요청에 역할·권한 필드를 함께 전송할 때 서버가 이를 반영하면 사용자가 스스로 권한을 상향할 수 있음
- 최고 관리자 권한 탈취와 동일한 효과로 전체 데이터 일괄 반출, 계정·설정 변조로 이어짐

**④ 기술적 보완 요구사항**

- 관리자 기능 전체에 서버측 역할 검증 및 기본 거부(Deny by Default) 원칙 적용
- 수정 요청은 허용 필드만 반영하는 허용 목록(Allow-list) 방식으로 처리
- 역할별 권한 매트릭스(역할 × 기능 × 허용 여부) 문서화

---

### B-3. 대용량 파일 다운로드 IDOR 및 무제한 반출

**① 위협명 및 위험도**

- 순차적 식별자 열거를 통한 자동 수집(스크래핑) 및 요청량 제한 부재로 인한 대량 반출
- 위험도: **Critical**

**② 관련 근거**

- [R6] API4(무제한 자원 소비), API1(객체 수준 권한 검증 실패), [R7] V4(접근 통제), V8(데이터 보호)
- [R3] 제6조(유출 시도 탐지·대응), 제8조(다운로드 사유 확인)

**③ 현상 및 시스템 영향도**

- 다운로드 주소에 순차 번호만 포함되고 요청마다 권한을 재검증하지 않으면, 번호를 바꾸는 자동화로 전체 파일을 수집할 수 있음
- 임시 다운로드 링크에 유효기간·사용 횟수 제한이 없으면 노출된 링크가 제3자에게 재사용됨
- 요청 속도·다운로드량 제한이 없으면 단일 계정으로 짧은 시간에 대량 반출이 가능하며, 정상 다운로드처럼 보여 탐지가 어려움
- 연구대상자 전체의 임상·건강정보 대량 유출로 확대될 수 있음

**④ 기술적 보완 요구사항**

- 다운로드 요청마다 서버측 권한 재검증
- 일회성·단기 유효 서명 URL 적용, 식별자를 UUID 등 추정 불가능한 값으로 전환
- 계정별 요청 속도 제한(Rate Limit), 다운로드량 상한, 대량 다운로드 사전 승인 절차 도입
- 대량 다운로드 발생 시 실시간 경보 및 사유 확인(A-5 연계)

---

## 4. 국정원 보안성 검토 대비 외주 운영사 제출 요구 서면 증빙 체크리스트

### 4.1 제출 원칙

- 외주 운영사는 각 항목에 대해 "적용/미적용" 답변에 그치지 않고 **증빙 자료를 첨부하여 서면으로 회신**함
- 증빙은 운영 환경 기준이어야 하며, 개발·시험 환경 자료는 인정하지 않음
- 미조치 항목은 조치 계획과 완료 예정일을 함께 제출함

### 4.3 회신 검토 기준

- 증빙 없이 "조치 완료"만 회신된 항목은 **미확인**으로 분류하고 재요청함
- "확인 불가" 또는 "기록 없음"으로 회신된 항목은 **통제 부재**로 간주하여 즉시·단기 조치 대상에 포함함
- 미조치 항목은 완료 예정일 기준으로 이행 여부를 재점검함

### 5.4 이행 관리

- 단계별 완료 여부는 외주사 제출 증빙으로 확인하며, 증빙이 없는 항목은 미완료로 관리함
